# Re-run, 2026-09-08 — dead end #2, falsified in both directions

This supersedes **nothing** in `README.md` or `WIRE-FRAMES.md`. Those files record
UAT on 2026-09-07 and are still an accurate record of that deployment, which has
**not** been redeployed. What this file adds is a second measurement of one stage,
on a target that runs the repaired code.

| file | target | code | what it shows |
|---|---|---|---|
| `wire/stn_128b63f1.ndjson` | UAT | as deployed 09-07 | the original traversal. Unchanged. |
| `wire/stn_f297ceb1-local-BEFORE.ndjson` | local stack | **before** the repair | reproduces dead end #2 off UAT |
| `wire/stn_f297ceb1-local-AFTER.ndjson` | local stack | **after** the repair | the command is answered |

## Why the re-run is local and not UAT

The instruction for this cycle was **do not deploy**. UAT runs a built image, so a
re-run there measures the old code and can only re-confirm the capture. The local
stack mounts the working tree, so it is the only target where the repair is live.

The cost of that choice is stated rather than hidden: the local broker is the same
EMQX 5.8 image and the same mTLS listener, but it is **not** UAT, and the station is
freshly provisioned rather than one of UAT's. What the local pair does establish is
the thing in dispute — that the ordering is a property of the server's code and not
of the environment — because **both** local runs used the same broker, the same
station, the same certificate and the same simulator build. Only the server code
differs between them.

## Stage 3 (boot) — the frames, both runs

Same station `stn_f297ceb1`, same broker, minutes apart.

### BEFORE — reproduces the UAT capture exactly

```
#8   22:21:12.240 in   ChangeConfiguration    Request   mac=y
#9   22:21:12.240 out  puback
#10  22:21:12.545 in   BootNotification       Response  mac=-
#11  22:21:12.578 out  StatusNotification     Event     mac=y
```

Station-side, in its own words:

```
[MessageRouter] REFUSED ChangeConfiguration on ospp/v1/stations/stn_f297ceb1/to-station:
no session key held, so it cannot be verified (1013 MAC_MISSING)
```

**No response to the command.** It dies exactly as `#11`–`#13` on UAT did:
`ChangeConfiguration` first, Boot Response second, silence.

### AFTER — the order is inverted, and the command is answered

```
#8   22:25:15.487 out  BootNotification       Request   mac=-
#10  22:25:19.950 in   BootNotification       Response  mac=-     <- the key arrives
#11  22:25:20.026 out  StatusNotification     Event     mac=y
#14  22:25:20.029 out  StatusNotification     Event     mac=y
#16  22:25:20.142 in   ChangeConfiguration    Request   mac=y
#17  22:25:20.151 out  ChangeConfiguration    Response  mac=y     <- ANSWERED
```

`REFUSED ChangeConfiguration` occurrences in the station log: **0**, against 1 in the
BEFORE run.

The frame that matters is `#17`. The original capture's dead end #2 was not only that
the command arrived early — it was that the station *published no error response*, so
the command simply died and expired server-side. There is now a Response, it carries a
`mac`, and it is on the wire 9 ms after the command.

## What the re-run found that the repair had missed

The first AFTER attempt came back with the frames still in the **old** order, with the
repair already merged. That was not noise, and it is the reason this re-run was worth
doing: there are **two** consumer paths on the server and only one had been fixed.

| path | reached by |
|---|---|
| `app/Shared/MQTT/Listeners/ProcessMqttMessage.php` | the internal simulate route, and the server's own tests |
| `app/Console/Commands/MqttConsume.php` | bridge → `mqtt:incoming` → worker — **every deployed environment** |

The server's suite was green over the defect, because nothing in it drove the worker.
A source-enumerating gate now requires every site that answers a station to sit inside
the ordering scope, and it was RED-tested by removing the bracket again.

## How to reproduce the local pair

The local stack has no seeded stations and its pool bootstrap is UAT-bound (it shells
into UAT's Postgres), so the station was provisioned by driving the same REST chain the
traversal used, against `http://localhost:8080`, as `admin@csms.local`. Two local
deviations, both recorded because they are preconditions and not conveniences:

1. `MQTT_WORKER_ENABLED=false` in the local environment, so `mqtt:consume` exits
   cleanly and nothing consumes the bridge's list. It was started for the run with the
   flag overridden, and stopped afterwards.
2. Provisioning returns `mqtts://csms-emqx.localhost:8883`, and the broker's server
   certificate does not carry that altname, so the TLS handshake fails
   `ERR_TLS_CERT_ALTNAME_INVALID`. The persisted `-mqtt.json` artefact was pointed at
   `mqtts://localhost:8883` for the run. This is the local mirror of surprise #1 in
   `README.md` — the station's own provisioning directive is not usable as given.

Teardown followed the same FK-ordered SQL as the original run.
